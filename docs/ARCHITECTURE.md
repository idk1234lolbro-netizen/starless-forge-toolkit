# Starless Forge Toolkit Architecture

## Purpose

Starless Forge Toolkit is an internal generation toolkit for Nova AI. It provides reusable systems that turn a structured character description into a clean, usable 3D character asset.

It is not intended to be a manual modelling application. Nova should make the creative decisions and invoke the toolkit; people should not need to sculpt, place vertices, or operate Blender to get a character.

## Core principles

1. **AI-directed, tool-executed.** Nova interprets prompts and references, plans the character, and chooses parameters. Toolkit modules perform repeatable geometry and asset operations.
2. **Modular.** Face, body, hair, clothing, accessories, materials, and validation are separate capabilities with explicit inputs and outputs.
3. **Composable.** A character is assembled from modules rather than generated by one opaque function.
4. **Quality-aware.** Every generation stage reports warnings and measurable checks. A successful function call is not proof of a production-ready model.
5. **Reproducible.** Given the same inputs, seed, and compatible version, procedural operations should produce the same result where practical.
6. **No mandatory DCC dependency.** The core workflow must not require Blender or another desktop modelling application. Optional import/export adapters may be added later.
7. **Honest about limitations.** A single image does not reveal hidden anatomy or the back of a character. The system must represent uncertainty rather than silently inventing reference details.

## High-level pipeline

```text
Prompt / reference images
          |
          v
Nova: interpretation and planning
          |
          v
Normalized CharacterSpec
          |
          v
Generation plan and dependency graph
          |
          v
Feature modules
(face, body, hair, clothing, accessories)
          |
          v
Assembly and geometry processing
          |
          v
Validation, diagnostics, optional repair
          |
          v
Materials + rig/export preparation
          |
          v
GLB / glTF and generation report
```

Nova is the orchestrator. The toolkit does not need to contain its own language model. It should expose clear functions and structured results that Nova can call.

## Main system boundaries

### 1. Character specification

A versioned, normalized data structure is the shared contract between Nova and the toolkit. It should contain only explicit or inferred properties, with confidence/provenance where useful.

Examples of information:
- overall style and intended level of realism
- body proportions and silhouette
- face shape and feature descriptions
- hair style, length, shape, and colour
- clothing layers and accessories
- material descriptions
- pose and output requirements
- reference-image associations and uncertain details

The schema must distinguish a user-specified fact from an AI inference. Missing information should use documented defaults or remain unspecified; it should not be disguised as certainty.

### 2. Generation modules

Each module owns one domain and exposes a stable interface. Modules should accept normalized parameters, return geometry/material data plus diagnostics, and avoid reaching into unrelated modules' internals.

Initial module candidates:
- body and proportions
- face and facial features
- hair construction
- clothing and fabric
- accessories and equipment
- materials and surface appearance

The first implementation module will be selected only after the existing repository and runtime are inspected. Do not duplicate an existing generator.

### 3. Geometry and assembly

Shared geometry utilities handle coordinate conventions, transforms, mesh merging, normals, topology checks, bounds, and other low-level operations. Feature modules should reuse these utilities rather than each implementing incompatible versions.

### 4. Validation and repair

Validation is a first-class stage. It should report issues such as:
- empty or non-finite geometry
- invalid indices or malformed attributes
- missing normals or material assignments
- unexpected scale or bounds
- disconnected pieces where connectivity is expected
- obvious intersections or gaps where checks are available
- export failures

Repairs must be explicit and reported. Never silently change the character's design to make a validation check pass.

### 5. Export

The initial target should be GLB/glTF because it is widely supported by web and 3D viewers. Export must preserve geometry, materials, transforms, and metadata supported by the chosen exporter. Rigging and animation should be added as a separately tested capability, not assumed to exist.

## Decisions intentionally left open

The repository currently contains only a minimal README. Before choosing dependencies or writing generator code, inspect the full project context and confirm:
- JavaScript versus TypeScript
- existing Three.js version and rendering/runtime constraints
- Node/browser support requirements
- test runner and formatting conventions
- desired export implementation
- whether any useful generation code already exists elsewhere in the project

Avoid adding large AI model weights or heavyweight services to the core package. AI inference should remain outside the geometry toolkit unless a specific, justified capability requires it.
